# security-scan · 分层代码安全扫描

## 为什么按这个方法做

绝大多数真实漏洞不是「一行显眼的危险代码」。用户可控的数据往往要经过若干函数、跨越几个模块，最后才进入网络请求、文件写入、数据库查询或系统命令。孤立地看其中任何一个文件，都还原不出完整的风险路径——所以**按危险函数名做正则匹配注定既漏又吵**：漏掉跨文件的链路，同时把一堆本就安全的调用报成漏洞。

本技能的定位因此是：**规则只负责快速定位候选点，判定必须由你读代码建立可核验的因果链**。一条 finding 值不值得写进报告，看的不是「命中了哪条规则」，而是你能不能说清楚三件事——数据从哪个不可信入口来、经过哪几跳抵达危险汇聚点、路径上的校验为什么防不住。说不清就不写。

同样重要的是**扫完不等于做完**。安全反馈只有走完「发现 → 理解 → 修复 → 跑测试 → 复扫」才真正落地，中途停在一份告警清单上，成本只是从扫描转嫁给了下一个人。

本技能与人工代码审查、渗透测试、SAST、SCA、组织现有安全流程是互补关系，不替代它们。

## 四种模式与意图路由

| 模式 | 扫描范围 | 分析强度 | 典型时机 |
|---|---|---|---|
| **L1 静态快检** | 本轮刚生成 / 刚改动的代码片段 | 高危模式匹配，秒级 | 写完代码随手一扫；或装成 hook 常开 |
| **L2 轻量扫描** | 工作区未提交的增量变更 | 语义理解单个变更的可控性与汇聚点 | 单个编码任务收尾时 |
| **L3 深度扫描** | 已提交但尚未审查的变更 + 其跨文件调用链 | 跨文件跨函数完整数据流追踪 | 提交后、推送 / 发 PR / 发布 / 部署前 |
| **全量扫描** | 整仓，或用户指定的目录 / 文件 | 同 L3，按模块分治 | 整仓审计、接手陌生项目、安全专项 |

**路由规则**（用户怎么说 → 走哪个模式）：

- 明确点名层级（「轻量扫描」「L2」「深度扫描」「L3」「全量」）→ 照办。
- 「刚写完这段，看看有没有问题」「这段代码安全吗」→ L1 或 L2，按改动量选：几十行内 L1，成规模的功能改动 L2。
- 「提交前 / 交付前查一下」「这批改动有没有风险」→ L2。
- 「推送前 / 发 PR 前 / 发布前深度扫一遍」→ L3。
- 「扫 src/auth 目录」「扫整个仓库」「审一下这个模块」→ 全量扫描，范围取用户给的路径。
- 「扫描最近 3 个提交」→ L3，`--base HEAD~3`。
- **只说「做个安全扫描」没给范围** → 不要自己猜。先跑 `collect_scope.py --mode l2` 看工作区有没有改动：有改动就按 L2 起步并说明选择，没有改动再问用户扫哪儿。
- L3 若发现没有「已提交未审查」的变更（例如全部改动都还在工作区），退回 L2 并明确告知，不要空跑。

**扫描量上限**：单次扫描控制在 1 万行以内。超过就按目录或提交区间拆成多轮，每轮独立出一份报告，最后汇总——`collect_scope.py` 会在超限时给出 `over_limit` 标记和拆分建议。硬扛超大范围只会让分析变浅。

## 通用流程

`$SKILL` 指本技能所在目录（调用本技能时会告知其绝对路径）。产物统一落到目标项目的 `.tmp/security-scan/<时间戳>/`（该目录属于过程性文件，不入库）。
Windows 上若 `python` 不可用，改用 `py -3`；类 Unix 上用 `python3`。

### 第 1 步 · 定范围

```bash
python "$SKILL/scripts/collect_scope.py" --mode l2 --out .tmp/security-scan/<ts>/scope.json
# 其他：--mode l1 --path <文件>…   --mode l3 [--base <ref>]   --mode paths --path src/auth --path src/export   --mode repo
```

输出里要读三个数：`total_lines`（是否超限）、`languages`（决定读哪份语言笔记）、`files[].changed_lines`（L2/L3 的改动行范围，用于排优先级）。

### 第 2 步 · 规则预筛

```bash
python "$SKILL/scripts/prefilter.py" --scope .tmp/security-scan/<ts>/scope.json --out .tmp/security-scan/<ts>/candidates.json
```

产出候选点清单：每条带 `kind`（source / sink / sanitizer / secret / config）、`category`、`cwe`、`in_change`（是否落在本次改动行内）。

**候选点不是 finding，是待查线索。** 它的作用是告诉你「这个文件里有一次 `Runtime.exec`」「这个函数收了 `request.getParameter`」，省掉你逐行扫读的时间。接下来的判定完全由你负责。

同时也别被清单框住：预筛只认代码形状，认不出**逻辑类漏洞**。这类问题没有固定模式，靠盯着候选点清单永远发现不了，只能按「这次改动到底产生了什么」反查。下表左边一旦成立，右边就要人工过一遍——**即使预筛在那里零命中**：

| 改动引入了…… | 就要检查 |
|---|---|
| 新的对外接口，或通往既有代码的新调用路径 | 鉴权是否覆盖到、对象归属有没有校验、限流与配额、幂等与重放 |
| 新的对外响应，或新的错误分支（包括经统一响应 / 错误辅助函数返回的那些） | 把错误消息里插值进去的**每一个变量**逐个过：路径、异常对象、内部标识符、配置值。错误处理常常收敛到一两个辅助函数里，看着不像「错误分支」，最容易整片漏掉；成功与失败的响应差异也会泄露资源存不存在 |
| 新的落盘写入，或新的资源标识符 | 标识符是否可预测（时间戳、自增、顺序）；会不会静默覆盖既有数据；失败后残留怎么处理 |
| 新的配置项或默认值 | 默认是否安全；把某个开关关掉会发生什么 |
| 对既有的校验、异常处理、权限判断的修改 | 是收紧了还是放宽了——**放宽即为本次新引入的问题**，哪怕那段代码看着「本来就在」 |

### 第 3 步 · 语义验证（三问闸门）

对每个值得看的候选点，按下面三问逐个过。**三问全部答得上来才算 finding；任何一问答不上来，要么继续读代码把它答上来，要么就不上报。**

**① 可控吗？** 这个数据真的来自不可信输入吗？
需要给出具体入口的 `file:line` 和它的信任边界：HTTP 参数 / 请求体 / 请求头 / Cookie、上传的文件名与内容、URL 路径段、命令行参数、环境变量、第三方服务响应、消息队列、从数据库回读的曾经由用户写入的字段。
「它是个函数参数」不构成可控——要追到最外层调用方。若所有调用方传的都是常量或受信配置，那就不是漏洞，记进 `not_reported` 说明理由。

**② 可达吗？** 从入口到危险汇聚点是否存在真实调用链？
逐跳给出 `file:line`。中途每一个分支、鉴权判断、类型转换、长度限制都要交代：它是让链路断了，还是只是提高了利用门槛？若链路依赖某个前置条件（需登录、需管理员、需特定配置开启），写进触发条件，并据此调整严重级别——**别把「需要管理员权限」当成不是漏洞，也别把它当成和未认证同等严重**。

**③ 可绕吗？** 路径上的校验 / 转义 / 过滤，在这个具体位置真的防住了吗？
**看名字不算数，必须读实现。** `sanitize()`、`clean()`、`escape()`、`isValid()` 这些名字什么都不保证。要回答的是：它过滤了什么、漏了什么、以及**在这个汇聚点的语法位置上它是否适用**。
几个反复出现的形态：只过滤单引号但值拼进的是 `ORDER BY` 子句；只检查字符串表面含不含 `..` 但没规范化最终路径；在解码之前做的校验，解码之后被绕过；对 SQL **值**做了参数绑定但表名 / 列名是拼接的；白名单校验完之后又用了原始变量而非校验后的副本。

三问之外，还有两条一直生效的判断：

- **区分「用了某个 API」和「构成漏洞」。** 发起网络请求不等于 SSRF，执行子进程不等于命令注入，拼字符串不等于注入。差别在于攻击者能否控制其中的关键部分。
- **区分产品意图和安全后果。** 「支持传入更多 FFmpeg 选项」是合理需求，「允许外部字符串改变 shell 命令结构」是安全后果——两者可以同时成立，报告要写清楚是后者出了问题，而不是否定前者这个需求。

判定时按需读 `references/lang/<语言>.md`，那里是各语言真实汇聚点、伪净化函数和反直觉陷阱的清单。方法论细节和各漏洞类别的核查项在 `references/taint-analysis.md`。

### 第 4 步 · 交叉复核（L3 与全量扫描必做）

规模大的扫描要靠并行子 Agent 分治，并对结论做独立复核——这是压低误报的关键环节，也是单 Agent 一路读下来最容易糊弄过去的环节。

**分治**：把候选点按「模块 + 漏洞类别」聚成 3–6 组（上限 8），每组派一个子 Agent。给每个子 Agent 的指令要包含：负责的候选点清单、`references/taint-analysis.md` 与对应语言笔记的路径、三问闸门、以及「可以读仓库任意文件以追完调用链，但只对分到的候选点下结论」。要求它返回结构化 findings（字段见 `references/report-format.md`）。
分治的边界是**候选点**不是文件——链路会跨文件，子 Agent 必须能自由读全仓，否则链一断就漏报。

**复核**：每条 Critical / High 的 finding，各派一个独立子 Agent 做对抗式复核。复核 Agent 的指令是**默认这条 finding 不成立，去找它站不住的理由**：入口其实不可控？中间有分支断了链路？净化其实有效？位置或行号对不上？它只拿到 finding 内容和仓库，不拿到原分析过程，避免被既有结论带跑。反驳不成立才保留。
Medium 数量多时抽复核（至少覆盖一半），Low / Info 不复核。

主 Agent 负责汇总：合并重复（同一条链路被多个子 Agent 报出只留一条，取证据最全的那份）、统一编号、把被复核推翻的条目移进 `not_reported` 并注明推翻理由。

L1 / L2 范围小，单 Agent 完成即可，不必分治——为几十行改动拉起一队子 Agent 是纯粹的浪费。

### 第 5 步 · 出报告

把结论写成 `findings.json`（字段规范见 `references/report-format.md`），然后渲染：

```bash
python "$SKILL/scripts/render_report.py" --findings .tmp/security-scan/<ts>/findings.json --out-dir .tmp/security-scan/<ts>/
```

生成 `report.md` 与 `report.html`（自包含单文件，可直接用浏览器打开）。

会话里同时给出摘要表，让用户不打开文件也能判断要不要处理：

```
| # | 严重级别 | 问题 | CWE · OWASP | 位置 | 置信度 |
```

后面跟一句总体判断（能不能提交 / 能不能推送）和一句下一步建议。**别把整份报告正文糊在终端里**——长报告在终端里翻不动，这正是要落盘的原因。

`not_reported`（查过但判定不成立的候选点）必须写进报告。它和 findings 同等重要：它证明这些点被看过而不是被漏过，也让下次扫描不必重复推翻同样的疑点。

### 第 6 步 · 修复闭环（改代码前必须确认）

报告出完就停下来，把选择权交回用户。**不要顺手就改。**

用户确认要修之后，按这个顺序走，一条一条来：

1. **先说清打算怎么改**，尤其是修复会不会影响原有功能。修复方案优先级：结构化传参（参数绑定、`execFile`/`ProcessBuilder` 数组形式、结构化路径 API）> 允许列表 > 规范化后再校验 > 字符串过滤。**把字符串过滤当首选修复手段基本都是错的**——它总有漏网的编码形式，且下一个改这段代码的人看不出边界在哪。
2. **保住原有业务目标**。修复不能把需求本身砍掉：SSRF 的修法是给协议和目标地址划边界，不是删掉「从 URL 导入」这个功能。
3. **改完跑项目原有测试**，确认功能没被改坏。测试失败就是修复没做完，不许注释或跳过测试让它变绿。
4. **补一条针对该漏洞的测试**（能构造出来的话），让同类问题以后能被测试挡住。
5. **复扫**：重跑同一模式同一范围，确认同路径同类风险不再出现。复扫仍报同一条，说明修复没生效或只堵了一半，回到第 1 步。
6. **更新报告**：把 `fix_status` 改成 `fixed`，重跑 `render_report.py`，产出修复后的报告。

修复过程遵守项目既有规范：只改必须改的地方，匹配现有代码风格，注释用中文。

## 判定纪律速查

- **默认不成立。** 举证责任在「这是漏洞」这一侧，不在「这不是漏洞」那一侧。
- **每条 finding 必须能指到具体行。** 指不到具体行的结论是猜测，不是发现。
- **行号必须核对过。** 报错位置是报告可信度的第一印象，行号错了整份报告都掉价。
- **没有「可能存在」这种严重级别。** 拿不准就标 `confidence: needs-review` 并写清楚卡在哪一问，而不是含糊其辞地报个 High。
- **影响写到你能证明为止，多一步都不要写。** 「能覆盖这个文件」不等于「能执行代码」——先去确认文件权限位有没有执行权、那个文件到底会不会被加载执行、需不需要重启、重启时会不会重新拉取覆盖掉。把拒绝服务说成 RCE、把信息泄露说成接管，不只是这一条不准：它会让整份报告的可信度打折，也让真正的 Critical 失去分量。定级跟着证据走——影响段一旦吹大，severity 几乎必然跟着虚高一档。
- **不为凑数上报。** 零 finding 是完全正常的结论，写清楚扫了什么、查了哪些候选点、为什么都不成立即可。编出几条无关痛痒的「建议加强输入校验」只会稀释真问题。
- **不重复上报同一条链路。** 同一污点链在三个文件里各报一次，读的人会以为有三个漏洞。
- **「既有问题」不是免检牌。** 本次改动之前就存在的缺陷，默认不算本次引入——但下结论前先过三问：本次改动有没有**新增一条抵达它的路径**？有没有**收窄或移除**原本挡着它的防护？有没有**扩大**喂给它的可控输入？任一为是，它就是本次引入的风险，照常上报，只在标题里写明「既有缺陷，本次改动使其可达/加剧」。
  判断标准就是**你自己写下的那句话**：只要排除理由里出现了「本次改动新增了一条抵达它的路径」「本次把 X 收窄成了 Y」「本次只是多了个触发点」这类表述，这条就不该待在 `not_reported` 里——原地挪进 findings，严重级别按新的可达性重新定。承认了成因却仍然排除，是增量扫描最常见的漏报来源。
- **「取决于配置 / 取决于调用方 / 由上层决定」不是结论，是待办。** 说出这句话就意味着还差一步没走完：去读默认值、读框架的默认行为、grep 出真实调用点。仓库就在手边，查得到就按事实定论。只有跨服务、闭源依赖内部、纯运行时才能确定这类**真的查不到**的情况，才降为 `confidence: needs-review` 并写清卡在哪一环。

## 不应上报的情况

以下命中通常不构成 finding，按情况记进 `not_reported`：

- **测试代码、fixture、示例、文档片段、迁移脚本**里的危险调用——除非它们会被打进产物或在生产环境执行。
- **纯本地 CLI 工具**处理自己的命令行参数：使用者就是「攻击者」，没有信任边界可越。
- **数据来自受信配置**（应用自己的配置文件、代码常量、部署时注入的环境变量），且配置本身不由外部写入。
- **框架已统一处理**，例如 ORM 参数绑定、模板引擎默认转义、框架自带的 CSRF/XSS 防护——但**必须确认它在这个具体位置生效**，比如模板里用了 `|safe` / `v-html` / `dangerouslySetInnerHTML` 就等于自己关掉了防护。
- **依赖库自身的已知 CVE**：那是 SCA 的活，不是本技能的输出。可以在报告末尾提一句建议跑依赖扫描，别混进 findings 表。
- **纯代码风格、可读性、性能问题**：不是安全问题，不进这份报告。

## L1 常开快检（可选 hook）

L1 除了当作手动模式跑，还可以装成 Claude Code 的 `PostToolUse` 钩子，在每次 Edit / Write 之后自动对刚写入的内容做高危模式快检，命中就把提示回流给模型，在下一轮改动里处理掉。

```bash
# 手动对单个文件跑 L1
python "$SKILL/scripts/l1_check.py" --file src/foo.py

# 安装钩子（先看看会写什么，再决定）
python "$SKILL/scripts/install_l1_hook.py" --scope project --dry-run
python "$SKILL/scripts/install_l1_hook.py" --scope project
```

**装钩子会修改 `settings.json`，属于配置文件改动——只有用户明确要求安装时才执行，绝不能顺手装上。** 先跑 `--dry-run` 把将要写入的内容给用户看，得到同意再实际写入。脚本会自动备份原文件、做合并而不是覆盖，且重复安装不会产生重复条目。卸载用 `--uninstall`。

## 边界

说清楚能力边界本身就是安全工作的一部分，交付报告时一并讲明：

- 扫描面向当前任务代码与增量变更（全量模式面向指定范围），**不是完整安全审计，不保证发现所有漏洞**。
- 结果取决于可读到的代码上下文。跨服务调用、运行时动态加载、反射与配置驱动的行为、闭源依赖内部逻辑，都可能超出可分析范围。
- 只做静态分析，不构造攻击载荷、不对任何运行中的系统发起实际攻击、不做渗透测试。
- 关键业务代码仍需人工安全评审、依赖扫描和组织既有安全流程配合。
