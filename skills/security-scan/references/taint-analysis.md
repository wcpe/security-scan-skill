## 一、模型

一条漏洞就是一条链：

```
source（不可信入口） → propagation（若干跳传播） → [sanitizer?] → sink（危险汇聚点）
```

四个要素缺一不可：

- **source** 攻击者能左右取值的地方。
- **propagation** 数据流经的赋值、函数调用、拼接、编解码、序列化。每一跳都可能改变它的形态（URL 编码、Base64、JSON 反序列化），也可能在此丢失可控性（被换成枚举值、被 hash、被替换成 ID 查出来的对象）。
- **sanitizer** 路径上任何声称在做校验 / 转义 / 过滤的东西。**有没有不重要，有效才重要。**
- **sink** 数据抵达后会产生外部效果的调用：执行命令、拼 SQL、写文件、发请求、渲染 HTML、反序列化、加载类。

预筛脚本能标出可能的 source 和 sink，但**中间那段传播是它看不见的**，恰恰也是判定成不成立的关键。

## 二、可控性怎么判（第一问）

按信任等级排，越靠上越可控：

| 等级 | 入口 | 说明 |
|---|---|---|
| 完全可控 | HTTP query / body / path / header / cookie、上传文件的文件名与内容、WebSocket 消息、消息队列负载 | 未认证攻击者即可构造 |
| 认证后可控 | 登录用户提交的任何字段、用户设置、备注、昵称、上传内容 | 门槛是「有个账号」，通常仍算可控 |
| 特权后可控 | 仅管理员能填的配置项、后台参数 | 仍是漏洞（越权 / 内鬼 / 管理员账号被盗后的提权面），但严重级别下调 |
| 间接可控 | 从数据库回读的字段（若曾由用户写入）、第三方服务响应、被解析的外部文件内容、DNS / 重定向结果 | **二阶注入的来源，最容易被漏掉** |
| 环境可控 | 环境变量、命令行参数、本地配置文件 | 取决于部署形态：多租户服务里可能可控，本地 CLI 工具里通常不可控 |
| 不可控 | 代码常量、编译期确定的枚举、应用自己写死的配置 | 不构成 source |

判定要点：

- **追到最外层调用方为止。** 一个函数收了 `String name` 不代表 name 可控——去看所有调用它的地方传了什么。若全部是常量或受信来源，就不成立。
- **别忽略二阶。** 「先存进数据库，之后再取出来拼进 SQL / 命令」是最常被漏的形态：写入点看着安全（用了参数绑定），读出后的使用点才是汇聚点。
- **注意反序列化后的对象。** JSON / YAML / protobuf 反序列化出来的字段，可控性等同于原始报文。
- **注意「看起来受控」的字段。** 文件的扩展名、Content-Type、`Referer`、`X-Forwarded-For`、`Host` 头都是攻击者可写的。

## 三、可达性怎么判（第二问）

从 source 逐跳追到 sink，每一跳都要给出 `file:line`。追踪时盯住这几种会改变结论的情况：

- **分支断链**：`if (isAdmin)` 之后才到 sink → 链路仍成立，但触发条件是「管理员」。`if (!isValid) return;` 之后才到 sink → 要看 `isValid` 到底校验了什么（回到第三问）。
- **类型收敛**：字符串被 `parseInt` / `UUID.fromString` / 枚举 `valueOf` 转换后，注入空间通常消失。这是真正的断链。
- **重新取值**：校验的是 `input`，但传给 sink 的是原始的 `req.query.x` —— 这是「校验了却没用上」的经典 bug，链路照样成立。
- **编解码边界**：校验发生在解码之前，而 sink 之前又解了一次码（URL 解码、Base64、Unicode 规范化、路径规范化）。**跨越编解码边界的校验基本都失效**。
- **跨文件 / 跨模块**：链路跨文件时必须把中间文件都读了。读不到（跨服务、动态加载、反射调用）就在报告里写明「链路在此处不可静态确定」，并把置信度降到 `needs-review`，不要脑补。
- **框架隐式调用**：注解驱动的拦截器、AOP、事件监听、序列化回调、`__wakeup` / `readObject` / `finalize`，都是没有显式调用点的跳。

## 四、净化有效性怎么判（第三问）

**必须读实现。名字不代表行为。** 判定分两层：

**第一层：它到底做了什么？** 打开 `sanitize()` / `clean()` / `check()` 的源码，逐条看它过滤 / 替换 / 拒绝了哪些字符或形态。

**第二层：在这个 sink 的语法位置上，它够不够？** 同一个转义在不同位置的有效性完全不同：

| sink 位置 | 有效的防护 | 常被误用的防护 |
|---|---|---|
| SQL 的**值** | 参数绑定 / 预编译 | 转义单引号（数字型注入不需要引号） |
| SQL 的**标识符**（表名、列名、`ORDER BY`、`GROUP BY`） | 允许列表映射到白名单常量 | 参数绑定（**根本绑不了标识符**）、转义引号 |
| shell 命令 | 数组形式传参、不经 shell、`shlex.quote` / `escapeshellarg` | 过滤 `;` `&` `\|`（漏掉 `` ` `` `$()` 换行 `\n`）、`escapeshellcmd`（不转义参数分隔） |
| 文件路径 | 规范化后校验仍以目标目录为前缀（比较时带上分隔符） | 只删 `../`（`....//` 还原）、只查字符串含不含 `..`（编码可绕）、`path.join` / `filepath.Clean`（不做归属约束） |
| HTML 文本节点 | 上下文相关的 HTML 转义 | 只过滤 `<script>` 标签 |
| HTML 属性 / URL / JS 上下文 | 对应上下文的编码 | 通用 HTML 转义（属性未加引号时无效；`javascript:` 协议未拦截） |
| URL 目标（SSRF） | 协议白名单 + 解析后校验 IP 不在内网 / 回环段 + **禁止跟随重定向或每跳都校验** | 校验字符串前缀（`http://evil.com@127.0.0.1`、DNS rebinding、重定向） |
| 反序列化 | 换安全解析器（`safe_load`）或类型白名单 | 过滤报文里的关键字 |
| 模板 | 模板本身固定，只把数据当参数传 | 过滤 `{{` `}}` |

其他反复出现的失效形态：

- **前缀比较不带分隔符**：`/data/user` 通过了 `startsWith("/data/user")`，`/data/user-evil` 也通过。
- **黑名单**：任何「禁止这些危险字符」的写法，都要假设它不完整。
- **只在前端 / 只在某一个入口校验**：另一个入口进来就绕过了。
- **大小写 / 编码差异**：`filter("../")` 挡不住 `..%2f`、`..\`、`%252e%252e%252f`。
- **把判断推给别人**：「是否透出给用户由上层决定」「取决于调用方怎么用」「看部署时怎么配」——这些不是判定，是还没查完。默认值写在框架配置里、调用点 grep 一下就有、模板的转义开关就在文件里。仓库在手边就去读；只有跨服务、闭源依赖内部、纯运行时才定这类真查不到的情况，才允许停在「未知」并降为 `needs-review`。

如果读完实现确认它**确实防住了**，把这条写进 `not_reported`，注明「路径上的 X 已在 Y 位置做了 Z，链路不成立」。这条记录本身是有价值的产出。

## 五、漏洞类别核查清单

每类给出：典型 sink → 判定要点 → 有效修复。

### 命令注入（CWE-78）
- **sink**：`system` / `exec` / `popen` / `Runtime.exec` / `ProcessBuilder` / `Process.Start` / `Command::new` / 反引号 / `%x{}`。
- **要点**：先分清**是否经过 shell**。经 shell（`sh -c`、`shell=True`、单字符串 exec、反引号）时元字符全部危险；不经 shell 时字符串不会被解释，风险转移到「程序名可控」和「参数被目标程序当成选项」（例如可控值以 `-` 开头，或注入 `--output=`）。
- **修复**：数组形式传参且程序名固定；确需拼接时用 `shlex.quote` / `escapeshellarg`；对可能以 `-` 开头的值加 `--` 分隔或做允许列表。

### SQL 注入（CWE-89）
- **sink**：拼接或插值进 `execute` / `query` / `createQuery` / `FromSqlRaw`；MyBatis 的 `${}`；ORM 的 raw / extra / order。
- **要点**：**值和标识符要分开看**。值用绑定即安全；表名、列名、排序字段、`LIMIT`/`OFFSET`（部分驱动）无法绑定，只能用允许列表。「已经用了 PreparedStatement」不构成安全结论——要看**这个具体位置**拼的是什么。另外注意二阶注入与 `LIKE` 通配符注入。
- **修复**：值走绑定；标识符映射到代码里写死的白名单集合（不是「校验字符集」，是「只能取这几个之一」）。

### 路径穿越 / Zip Slip（CWE-22）
- **sink**：文件读写、删除、移动、解压、静态文件服务。
- **要点**：可控部分可能是文件名、子目录、扩展名或整段路径。必须走「拼接 → 规范化 → 校验规范化结果仍以目标目录（含尾部分隔符）为前缀」三步。注意绝对路径覆盖（Java 的 `new File(base, "/etc/passwd")`、Node 的 `path.join` 后接绝对路径、.NET 的 `Path.Combine`、Rust 的 `PathBuf::join`）、符号链接、Windows 的 `\` 与盘符、以及压缩包条目名。
- **修复**：规范化后做前缀校验；或干脆不用用户提供的名字，改用生成的 ID + 单独存映射。

### SSRF（CWE-918）
- **sink**：服务端发起的 HTTP / gRPC / Redis / 文件协议请求。
- **要点**：URL 全部或部分可控（含只可控 host、path、或 query）。检查：协议是否限定；是否解析出 IP 并排除回环 / 私网 / 链路本地 / 元数据地址（`169.254.169.254`）；**是否跟随重定向**（跟随则每跳都要重新校验）；是否存在 DNS rebinding 窗口。
- **修复**：协议 + 域名允许列表；禁用重定向或逐跳校验；出网走独立的受限网络出口。

### 不安全反序列化（CWE-502）
- **sink**：`pickle.loads`、`yaml.load`、`Marshal.load`、`ObjectInputStream.readObject`、`BinaryFormatter`、Jackson 多态类型、`unserialize`。
- **要点**：只要输入不是完全受信，能实例化任意类型的反序列化就是 RCE 级别。看清楚有没有传安全的 Loader / Constructor / 类型白名单——**默认构造通常是不安全的那个**。
- **修复**：换安全解析器；用固定 schema 的数据格式（JSON + 显式字段映射）；确需多态时用显式类型白名单。

### XSS（CWE-79）
- **sink**：`innerHTML`、`document.write`、`dangerouslySetInnerHTML`、`v-html`、`html_safe`、`Html.Raw`、`template.HTML`、未转义的模板输出。
- **要点**：分清存储型 / 反射型 / DOM 型，以及输出上下文（文本、属性、URL、JS、CSS）——**转义方式必须匹配上下文**。框架默认转义时，重点看谁显式关掉了它。
- **修复**：保持框架默认转义；确需富文本时用成熟的白名单净化库（DOMPurify 等），不要自己写正则过滤。

### XXE（CWE-611）
- **sink**：XML 解析器工厂。
- **要点**：多数 XML 解析器默认允许外部实体（.NET 新版本、Python defusedxml 等已改默认）。要在代码里找到显式禁用 DTD / 外部实体的调用，找不到就成立。除读取本地文件外还能打 SSRF 与拒绝服务（十亿笑）。
- **修复**：禁用 DTD 与外部实体，或换 defusedxml 这类安全封装。

### 模板注入 SSTI（CWE-1336 / CWE-917）
- **sink**：把用户数据拼进**模板字符串本身**（而不是作为变量传入）；SpEL / OGNL / MVEL 表达式求值。
- **要点**：区分「模板里渲染用户数据」（正常）与「用户数据成为模板的一部分」（SSTI）。多数模板引擎的 SSTI 可直接升级为 RCE。
- **修复**：模板固定在代码里，用户数据只经参数传入。

### 代码注入 / 动态求值（CWE-94）
- **sink**：`eval`、`exec`、`new Function`、`GroovyShell`、`ScriptEngine`、`instance_eval`、`Assembly.Load`、可控方法名的 `send` / 反射调用。
- **要点**：几乎没有「安全地 eval 用户输入」的写法。可控的方法名 / 类名同样危险。
- **修复**：换成显式的映射表（字符串 → 允许的函数），不要动态求值。

### 越权（CWE-639 / CWE-862 / CWE-863）
- **要点**：**预筛完全看不到这一类，必须人工过。** 每个按 ID 访问对象的接口都问三句：有没有校验当前用户对这个对象的归属或权限？校验用的是请求里的身份还是会话里的身份（前者可伪造）？同一资源的其他入口（导出、批量、搜索、旧版接口）是否也做了同样校验？
- **修复**：把权限校验下沉到数据访问层（查询条件带上 owner），而不是散落在各个 controller。

### 认证与会话（CWE-287 / CWE-384 / CWE-613）
- **要点**：JWT 是否验签、是否限定算法（拒绝 `none` 与算法混淆）、是否校验过期与受众；口令是否用 bcrypt / scrypt / argon2 而非 md5+盐；登录成功后是否轮换 session id；退出登录是否真的失效服务端会话；重置口令令牌是否一次性、有时效、足够随机。

### 开放重定向（CWE-601）
- **要点**：跳转目标可控。常被低估——它是钓鱼与 OAuth 回调劫持的跳板。校验必须解析 URL 后比对 host，而不是比对字符串前缀。

### 加密与随机数（CWE-327 / CWE-338 / CWE-330）
- **要点**：安全用途（令牌、会话 ID、重置码、盐、IV、口令）必须用密码学安全随机源。ECB 模式、静态 IV、自研加密都是问题。MD5 / SHA-1 用于文件校验和无碍，用于口令或签名不行。

### 硬编码凭据（CWE-798）
- **要点**：确认不是占位符 / 测试常量 / 已失效的示例。真凭据要同时给出两件事：**从代码中移除**，以及**轮换该凭据**（已经进过版本库的密钥必须视为已泄露）。报告与日志里一律脱敏，不写完整值。

### 竞态 / TOCTOU（CWE-367 / CWE-362）
- **要点**：检查与使用之间存在窗口（先 `exists()` 再 `open()`、先查余额再扣款、先查重再插入）。并发路径上共享的可变状态是否有锁或原子操作、事务隔离级别是否够。

### 原型链污染 / 批量赋值（CWE-1321 / CWE-915）
- **要点**：把外部对象递归合并进内部对象（`_.merge`、`Object.assign` 到共享对象、`params.permit!`、直接 `Model(**request.json)`）。看有没有过滤 `__proto__` / `constructor` / `prototype`，以及是否显式限定了可赋值字段。

## 六、模式匹配看不见的那一半：逻辑类漏洞

预筛只认代码形状，下面这些没有固定形状，**改动一旦涉及就必须人工过一遍**：

- 权限与归属校验缺失或不一致（见上文越权）
- 认证绕过：某个分支提前 `return true`、调试开关、默认账号
- 业务规则被绕开：负数金额、超大数量导致整数溢出、跳过中间步骤直接调用最后一步
- 幂等与重放：支付回调、优惠券核销、验证码校验
- 限流与配额缺失：短信 / 邮件 / 验证码 / 昂贵查询接口
- 默认值不安全：默认开放、默认弱口令、默认允许所有来源
- 错误信息泄露：把堆栈、SQL 语句、内部路径、主机名返回给客户端；也包括成功与失败的响应差异泄露「这个资源存不存在」
- 日志泄露：把口令、令牌、完整身份证 / 银行卡写进日志
- 资源标识符可预测：文件名、令牌、订单号用时间戳、自增或顺序生成，可被枚举、抢占或撞名
- 写操作静默覆盖：落盘或入库时不做唯一化，同名直接覆盖既有数据（备份投毒、快照替换、头像互串）
- 失败后残留：中途出错时临时文件、半成品记录不清理，既占资源也可能被后续流程当成合法数据消费

## 七、常见误报形态

出报告前对着这张表过一遍，命中的就撤回到 `not_reported`：

1. **把「使用了某个 API」当成漏洞** —— 发请求 ≠ SSRF，起进程 ≠ 命令注入。
2. **source 其实不可控** —— 追到调用方全是常量。
3. **中间已经收敛** —— 被转成整数 / UUID / 枚举。
4. **净化确实有效** —— 读了实现，在这个位置够用。
5. **测试代码 / fixture / 示例 / 迁移脚本** —— 不进生产路径。
6. **本地 CLI 处理自己的参数** —— 没有信任边界。
7. **框架已经处理** —— 且确认在这个位置生效（没有 `|safe` / `Html.Raw` 之类的开口）。
8. **依赖库自身的 CVE** —— 那是 SCA 的范围，最多在报告末尾提一句。
9. **纯风格 / 性能 / 可读性问题** —— 不是安全问题。
10. **同一条链路重复上报** —— 合并成一条。

## 八、严重级别与置信度

**严重级别**由「影响 × 可达难度」共同决定，不是由漏洞类型决定：

| 级别 | 判据 |
|---|---|
| critical | 未认证即可触发的 RCE、认证绕过、任意文件读写、大规模数据泄露 |
| high | 需要普通账号即可触发的注入 / 越权 / 敏感数据泄露；或未认证可触发但影响面较窄 |
| medium | 需要特权账号或较苛刻前置条件；或影响有限（单条记录、需要用户交互） |
| low | 需要多个前置条件叠加、影响轻微，或属于纵深防御建议 |
| info | 不构成可利用问题，但值得知晓的安全相关事实 |

**置信度**独立于严重级别，表示证据的完整程度：

- `confirmed` —— 三问全部答完，链路每一跳都有 `file:line`。
- `likely` —— 链路清楚，但某一跳依赖静态无法完全确定的行为（反射、动态配置、跨服务）。
- `needs-review` —— 形态可疑但缺关键证据，需要人工或运行时验证。写清楚缺的是哪一环。

**不要用严重级别掩盖置信度不足。** 证据不全就标 `needs-review`，别为了引起重视而报 high。
